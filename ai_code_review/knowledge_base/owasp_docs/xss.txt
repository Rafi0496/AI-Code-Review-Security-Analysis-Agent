# Cross-Site Scripting (XSS) & Client-Side Code Injection — OWASP A03:2021 Master Reference

## 1. What is Cross-Site Scripting (XSS)?
Cross-Site Scripting (XSS) is a client-side code injection attack in which malicious scripts (typically JavaScript) are injected into otherwise trusted web applications. When an unsuspecting user loads a web page containing the malicious payload, the browser executes the script in the context of the user's active session.

Attackers leverage XSS to:
- Steal sensitive session cookies, JWT access tokens, and local storage data
- Capture user keystrokes (keylogging) and credentials
- Perform unauthorized actions via the victim's authenticated browser session (client-side CSRF)
- Deface websites, display phishing modals, or redirect users to malicious domains

- **OWASP Top 10 Category**: A03:2021 - Injection

- **CVSS v3.1 Score**: 6.1 - 9.0 (Medium to Critical)

## 3. The 3 Major Types of XSS

### 3.1 Stored XSS (Persistent XSS)
The malicious script is permanently stored in the target server's database (e.g. comment section, user profile bio, product review, forum post). When other users view the stored record, the script executes automatically. This is the most dangerous form of XSS.

### 3.2 Reflected XSS (Non-Persistent XSS)
The malicious payload is embedded in a URL parameter or HTTP request (e.g. search query, error message parameter) and immediately reflected back in the server's HTML response without sanitization.

### 3.3 DOM-Based XSS (Client-Side XSS)
The vulnerability exists entirely in client-side JavaScript. The server is not involved; client-side scripts read data from an untrusted Source (e.g. `location.search`, `location.hash`, `document.referrer`) and pass it to an unsafe Sink (e.g. `innerHTML`, `document.write`, `eval()`, `setTimeout()`).

---

## 4. Unsafe Sinks and Safe Alternatives in JavaScript

| Vulnerable Execution Sink | Safe Alternative |
|---------------------------|------------------|
| `element.innerHTML = data` | `element.textContent = data` or `DOMPurify.sanitize(data)` |
| `document.write(data)` | `document.createElement()` + `appendChild()` |
| `element.outerHTML = data` | `element.replaceWith()` |
| `eval(data)` / `new Function(data)` | `JSON.parse(data)` |
| `location.href = data` | Validate URL scheme against `https:` or use relative paths |

## 5. Defense-in-Depth Mitigation Architecture

### 5.1 Context-Aware Output Encoding
- **HTML Body Context**: Encode `&` -> `&amp;`, `<` -> `&lt;`, `>` -> `&gt;`, `"` -> `&quot;`, `'` -> `&#x27;`.
- **HTML Attribute Context**: Strict alphanumeric whitelist or HTML attribute encoding.
- **JavaScript Context**: JSON serialization with Unicode escaping (`json.dumps()` in Python).

### 5.2 Content Security Policy (CSP Level 3)
Deploy a restrictive Content Security Policy header that disallows inline script execution and restricts script sources to trusted origins with cryptographic nonces.

```http
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-rAnd0m123'; object-src 'none'; base-uri 'self';
```

### 5.3 Cookie Hardening
Set the `HttpOnly` flag on all sensitive authentication and session cookies so they cannot be accessed or stolen via `document.cookie` in the event of an XSS vulnerability.
