# Cross-Site Request Forgery (CSRF) & State-Changing Request Security — OWASP A01 / A07 Master Reference

## 1. What is CSRF?
Cross-Site Request Forgery (CSRF / XSRF) is an attack that forces an end user to execute unwanted, unauthorized actions on a web application in which they are currently authenticated. With a little help of social engineering (such as sending a link via email or chat), an attacker may trick the users of a web application into executing actions of the attacker's choosing.

If the victim is a normal user, a successful CSRF attack can force the user to perform state-changing requests like transferring funds, changing their password or email address, or making purchases. If the victim is an administrative account, CSRF can compromise the entire web application.

---

## 2. Formal Classifications & CWE Mappings
- **OWASP Top 10 Category**: A01:2021 (Broken Access Control) / A07:2021 (Identification and Authentication Failures)
- **CWE-352**: Cross-Site Request Forgery (CSRF)
- **CVSS v3.1 Score**: 8.8 (High)

---

## 3. How CSRF Works
1. The victim logs into `bank.com` and receives a valid session cookie.
2. Without logging out, the victim visits an attacker-controlled website `evil.com`.
3. `evil.com` contains a hidden form that automatically submits a POST request to `bank.com/transfer`:
```html
<!-- Malicious payload on evil.com -->
<form id="csrfForm" action="https://bank.com/api/transfer" method="POST">
    <input type="hidden" name="recipient" value="attacker_account_999" />
    <input type="hidden" name="amount" value="5000" />
</form>
<script>document.getElementById('csrfForm').submit();</script>
```
4. The victim's browser automatically attaches the `bank.com` session cookies to the cross-site request, and the bank processes the unauthorized transfer.

---

## 4. Remediation & Defense-in-Depth

### 4.1 Modern Primary Defense: `SameSite` Cookie Attribute
Configure all session and authentication cookies with `SameSite=Strict` or `SameSite=Lax`.

- `SameSite=Strict`: Cookies are NEVER sent on cross-site requests (highest security).
- `SameSite=Lax`: Cookies are withheld on cross-site subrequests (images, forms), but sent when navigating via top-level GET links.

```python
# SECURE (FastAPI / Starlette Cookie Configuration):
response.set_cookie(
    key="session_id",
    value=session_token,
    httponly=True,       # Defeats XSS cookie theft
    secure=True,         # Requires HTTPS
    samesite="Strict",   # Defeats CSRF
    max_age=3600
)
```

### 4.2 Anti-CSRF Synchronizer Token Pattern
Generate a cryptographically random, unpredictable token per session or per request, embed it into forms, and verify it on the server on all state-changing methods (POST, PUT, DELETE, PATCH).

```python
# SECURE (FastAPI / CSRF Token Middleware Verification):
import hmac
import secrets

def generate_csrf_token(session_id: str, secret_key: bytes) -> str:
    random_nonce = secrets.token_hex(16)
    signature = hmac.new(secret_key, f"{session_id}:{random_nonce}".encode('utf-8'), 'sha256').hexdigest()
    return f"{random_nonce}:{signature}"

def verify_csrf_token(token: str, session_id: str, secret_key: bytes) -> bool:
    try:
        random_nonce, signature = token.split(":")
        expected_sig = hmac.new(secret_key, f"{session_id}:{random_nonce}".encode('utf-8'), 'sha256').hexdigest()
        return hmac.compare_digest(signature, expected_sig)
    except Exception:
        return False
```

---

### 4.3 Custom Request Headers for REST APIs
Enforce custom request headers (e.g. `X-Requested-With: XMLHttpRequest` or `X-CSRF-Token`) on all JSON APIs. Standard HTML `<form>` elements cannot set custom headers, defeating classic browser CSRF.
